# How os-rust works (for people who have never seen an operating system)

This text explains, assuming no prior knowledge of operating systems,
what is happening when you run `cargo run` in this project and see a
colorful screen appear in QEMU.

## What does "booting without an operating system" mean?

Every program you have ever run on your computer — a browser, a text
editor, a game — runs **on top of** an operating system (Windows,
Linux, macOS). The operating system is what:

- decides which program uses the processor at each instant,
- controls access to files, screen, keyboard, network,
- protects one program from messing up another's memory.

When the computer is turned on, there is only hardware — no program is
"orchestrating" anything yet. It is the **BIOS** (a small program burned
into the motherboard's hardware) that runs first and does the first task:
find a bootable device (here, the virtual disk created by `bootimage`) and
load the first piece of code from it into memory — that code is what
"boots" the operating system.

`os-rust` does something unusual: instead of booting a Windows or Linux,
it boots **straight into our own Rust binary**. There is no Windows,
Linux, or any other operating system running underneath — only the BIOS,
then our code, and nothing else. That is why the screen that appears in
QEMU does not look like an ordinary terminal: **there is no terminal at
all** there, only the text screen that the binary itself drew, byte by byte.

## From the BIOS to our message on screen: the complete path

1. **QEMU powers on a virtual machine** and simulates the BIOS of an ordinary PC.
2. **The BIOS loads the *bootloader*** — a small program (generated by
   the `bootloader` crate, which `bootimage` packs into the boot disk) whose
   only task is to put the processor in the right mode (64-bit mode) and
   load our Rust binary into memory, at the address agreed between
   it and our `Cargo.toml`/custom target.
3. **The bootloader transfers control to `kernel_main`** — the function in
   `src/main.rs` marked with the `entry_point!` macro. From here on, the
   code running is **ours**, line by line, with no operating system
   layer in between.
4. **`kernel_main` clears the screen and writes the welcome message**
   by calling `println!`, which under the hood writes directly to a
   special memory address: `0xb8000`.

## Why `0xb8000`? The screen as memory

In VGA text mode (a very old video mode, but still supported by
practically every PC/QEMU), the video card continuously reads a fixed block
of memory starting at address `0xb8000` and draws on the screen what it finds
there: 25 lines by 80 columns, and each screen position corresponds to **2
bytes** in that memory — one byte with the ASCII character, another with the color
(foreground + background). In other words: **writing to the screen, in this mode, is
literally the same thing as writing to a memory address**. There is
no "drawing API", there is no graphics driver — it is just memory.

That is why `src/vga_buffer.rs` treats the screen as a 25×80 matrix of
positions (`Buffer`) and why every write uses the `volatile` crate: without it,
the Rust compiler could "optimize" and simply not really write to
that address (after all, from the compiler's point of view, nobody "reads" the
value back) — but the video hardware **reads** that address all the
time, so the write has to actually happen, in the right order. That is
also why that part of the code needs `unsafe`: the compiler has
no way to know, on its own, that `0xb8000` is a valid and special address —
we are the ones who guarantee that, and that is why we comment every `unsafe` block
explaining exactly why it is safe at that point.

## Why does the text scroll when it goes past one screen?

The screen has only 25 lines. When the text goes past the last line, instead
of crashing or writing outside the bounds of video memory, the code copies
each line one position up (line 2 becomes line 1, line 3 becomes
line 2, and so on) and clears the last line — giving the impression
that the text "goes up" on the screen, exactly as in an ordinary terminal.

## What happens when things go wrong: panic

In an ordinary Rust program (running on top of an operating system), a
`panic!` normally prints an error message to the terminal and the operating
system then ends the process. But here **there is no operating
system to end the process** — `os-rust` *is* everything that is
running on the virtual machine. If we simply stopped the processor without
doing anything, the audience would see a frozen screen with no explanation at all, which
would look like a defect.

Therefore, `src/panic.rs` intercepts any `panic!` of the program (via
`#[panic_handler]`, Rust's mechanism for saying "this is what should
happen when a panic occurs, since there is no operating system to
decide for us") and uses the same infrastructure for writing to `0xb8000` to
show a readable error message on the screen, before halting the CPU safely
(the `hlt` instruction, which literally pauses the processor). The code
also protects itself against the rare case of a panic happening *during* the
handling of another panic — in that case, it does not even try to write
again, it just halts the CPU, so as to never hang in a loop with no way out.

## The path of a key: from the keyboard to the screen

v1 only wrote to the screen. This version answers the natural question that comes
next: "can I type?". For that, `os-rust` needs to react to an
event that can happen at any moment — a key being pressed —
without asking "did a key arrive? and now? and now?" all the
time (which would waste the processor for nothing). The hardware's solution to this
is called an **interrupt**: the processor simply stops what it is
doing, handles the event, and goes back to where it was. It is a
completely different mechanism from "writing to the screen" (which is just memory) — here
there is a real control flow happening outside our
`kernel_main` function.

The complete path, from one end to the other:

1. **You press a key.** The keyboard (emulated by QEMU as a PS/2
   keyboard) sends a code to a small motherboard chip called the
   **8042 controller**. That code is not the letter itself — it is a number that
   identifies *which physical key* changed state, called a **scancode**. The
   8042 makes that scancode available for reading on a processor
   input/output port, port `0x60`.
2. **The 8042 notifies the 8259 PIC** ("Programmable Interrupt Controller", the chip
   that has existed since the original PC to manage hardware interrupts)
   that a keyboard event is pending. That notification is **IRQ1** — the
   interrupt line number 1, reserved for the keyboard since the first
   PCs.
3. **The 8259 PIC signals the processor.** Before this could work without
   confusion, `src/interrupts.rs` reprogrammed the PIC so that the numbers
   (vectors) it uses to notify the processor do not collide with the
   numbers the processor itself already reserves for its own internal
   errors (such as "invalid instruction" or "division by zero") — and masked
   all interrupt lines except IRQ1, so that only the keyboard
   can interrupt the processor in this demonstration.
4. **The processor consults the IDT** ("Interrupt Descriptor Table"): a
   table, also built in `src/interrupts.rs`, that says "when interrupt
   number X happens, divert execution to this specific function".
   For IRQ1, that function is our own
   `keyboard_interrupt_handler`, written in Rust.
5. **The handler reads the scancode from port `0x60` and returns control
   quickly.** On purpose, it does nothing more than that — it neither
   translates the scancode nor writes to the screen. It only stores the scancode in a
   small queue and tells the PIC "handled" (without that notice, called *EOI* —
   *end of interrupt* —, the PIC would never again let another key interrupt
   the processor). Keeping the handler short avoids a subtle problem: if it
   tried to write to the screen right in the middle of a write that the rest of the
   program was already doing, the two could lock up, each waiting for the
   other forever.
6. **Back to the main flow**, the idle loop of `kernel_main` (in
   `src/main.rs`) periodically drains that queue and calls
   `src/keyboard.rs` to **translate** each scancode into an ASCII character,
   according to the US QWERTY keyboard layout (the same physical key, on a
   Brazilian ABNT2 keyboard, would produce a different symbol — that is why the
   project documents the layout in the README instead of trying to guess).
7. **The translated character reaches `src/shell.rs`**, which decides what to
   do with it: if it is an ordinary letter or symbol, it stores it in the current line's
   buffer and echoes it to the screen (reusing the same `0xb8000` `Writer` from
   v1); if it is Enter, it interprets the whole line as a command; if it is
   Backspace, it erases the last character.

While no key is pressed, the processor does not spin in an empty
loop burning energy for nothing: the `hlt` instruction puts it to
"sleep" until the next interrupt — exactly the same IRQ1 we have just
described is what wakes it up again.

## The serial port: a second text channel, only for the host

Until here, the only way to "see" what `os-rust` was doing was to look at
the QEMU screen. That works well for a live demonstration, but it has
a problem for someone debugging an error: the QEMU screen has no real
scrollable history beyond what is already on it, you cannot easily
copy text from it, and it is also the screen the "audience" sees —
we do not want to pollute it with technical diagnostic messages.

The solution is a second communication channel, completely separate from the
screen: the **serial port**. Before networks existed, every PC already had a
serial port (also called a "COM port") — a physical connector that
sends and receives one byte at a time, a simple cable that connected two
computers (or a computer and a printer) directly. QEMU
emulates that port and connects it, on the other side, to the terminal where you typed
`cargo run` or `cargo test` — that is why `Cargo.toml` already had, since
before this milestone, the `-serial stdio` configuration for QEMU.

Just like the text-mode screen (explained above) is only a special memory
address, the serial port is controlled through **input and output
ports** (*I/O ports*): special processor addresses,
different from ordinary memory addresses, accessed with specific
instructions (`in`/`out` in assembly; in Rust, the `Port` type of the
`x86_64` crate hides this detail). The chip that implements the serial port
is called the **UART 16550**, and it is always at the same I/O address on a PC:
`0x3F8`. `src/serial.rs` uses the `uart_16550` crate to talk to that
chip: build a `SerialPort` pointing to `0x3F8`, call `.init()`
once, right at the start of boot, before any other diagnostic
message, and, from then on, writing text to it is as similar to
`println!` as possible — that is why the macros are called
`serial_print!`/`serial_println!`.

There is an important detail hidden in there: what if an interrupt handler
(for example, the breakpoint one) needs to write to the serial port *exactly*
in the middle of a write that the kernel's main flow was already doing?
Without care, the two would fight over the same resource and lock up, each waiting for the
other forever (a *deadlock*). The solution, in
`src/serial.rs`, is to disable interrupts during every write to the
serial port: if the main flow is in the middle of a write, it
literally cannot be interrupted until it finishes, so the handler
never gets to compete for the same resource while it is busy.

## A test runner without the standard library

Rust's normal testing mechanism (what runs when you type
`cargo test` in an ordinary project) depends on Rust's standard library
(`std`) — which does not exist here: `os-rust` has been `#![no_std]` since Milestone
0, because there is no operating system underneath to provide files,
threads, memory allocation, etc. Still, the Rust nightly compiler
has a mechanism designed for exactly this case, called
`custom_test_frameworks`: instead of using the default runner, the project
registers its own function that must run when someone marks an item with
the `#[test_case]` attribute.

Our runner (`test_runner`, in `src/lib.rs`) is deliberately
simple: it receives a list of everything marked with `#[test_case]`,
prints on the serial port how many items there are (`Running <N> tests`), runs each one in
order, and prints `[ok]` after each one that returns without an error. There
is no memory allocation anywhere in this: the list of tests is a
slice (`&[...]`) built by the compiler itself, of fixed size,
known at compile time.

The whole kernel is compiled *twice*: once normally (the binary that
`cargo run` uses) and once in "test mode" (what `cargo test` uses,
enabled by the `#[cfg(test)]` flag scattered through the code). Since integration
tests in `tests/` are separate files that depend on the kernel as
a library, the project had to gain a new `src/lib.rs` (in addition to the
already existing `src/main.rs`): the library contains all of the
kernel's modules and can be reused both by the production binary and by
each integration test, each one booting the kernel from scratch, in its
own independent QEMU process.

## From the kernel to the exit code: how the result reaches the host

Running the tests inside QEMU solves half the problem: and how does
`cargo test`, which is running on your real computer (the "host"),
know whether the tests *inside* the virtual machine passed or failed? QEMU
does not read the kernel's mind — it needs an explicit signal.

The answer is a virtual hardware device that QEMU itself
offers for this purpose, called `isa-debug-exit`: an I/O address
(`0xf4`, in this project) that, when the kernel writes a value to it, makes
the QEMU process **exit immediately**, using that value to
compose the exit code of the QEMU process itself. The exact formula is
`(value << 1) | 1` — so writing `0x10` makes QEMU exit with code
`33`, and writing `0x11` makes QEMU exit with code `35`. These two
values (`Success`/`Failed`) were chosen only because they are the same ones
used in the reference literature on building a kernel in Rust — the
important thing is that they do not collide with the exit codes that QEMU
itself already uses for its own internal errors.

But `35` (or `33`) are not exactly `0`/`1` — it would not be natural for
whoever runs `cargo test` to be expected to memorize those numbers. That is where
`bootimage` comes in, the tool that had already been packaging the kernel into a disk image
since Milestone 0: this project's `Cargo.toml` tells it, in
`test-success-exit-code = 33`, "when the QEMU process exits with
code 33, that means success — translate it to exit code `0` of
`cargo test` itself". Any other QEMU exit code (including
`35`, or the code used when `bootimage` needs to kill QEMU for
taking too long) remains non-zero. That is why, after
`cargo test`, `echo $?` is enough to know whether everything passed, without
having to read any line of text.

## The role of the timeout and what happens with a panic during a test

What if a test never finishes — for example, a `loop {}` by mistake? Without
some protection, `cargo test` would wait forever. That is why
`Cargo.toml` also defines `test-timeout = 60`: if a test binary
does not signal success or failure within that time, `bootimage` kills the
QEMU process by itself and reports failure to `cargo test` — sixty
seconds is much more than the whole suite normally takes, but still
short enough not to leave whoever is running the tests
waiting for too long.

And a `panic!` in the middle of a test? Since this project's target uses
`panic-strategy = "abort"` (defined in the custom target
`x86_64-os_rust.json`), there is no possibility of "catching" a
panic and continuing to run the rest of the program normally, as
would happen in an ordinary Rust program running on top of an operating system.
A panic here **ends the entire process** — so, in test mode, the
`#[panic_handler]` (a different version from the one used in `cargo run`, see
`src/lib.rs`) treats any panic as a failure: it writes `[failed]`
plus the location and message of the panic to the serial port, and signals
`QemuExitCode::Failed` to the host. Since the panic interrupts everything, no
test after it, in the same binary, gets to run — exactly the
behavior expected when something goes very wrong in the middle of the suite.

That same limitation is the reason there is a test quite different from the
others: `tests/should_panic.rs`. It exists to prove that, when the
kernel *should* panic in a certain situation, it really
does. But if a normal panic always means "failure", how do you test
that a panic *happened as expected*? The answer is that this file does not
use the ordinary test runner: it is its own complete program,
with its own `#[panic_handler]`, which treats the panic as **success**
(because it was exactly what was expected to happen) — and, if the
function under test finishes without panicking, that is what becomes a failure.

## How to write a new test

A unit test — which lives inside the very module being
tested, like the ones that already exist in `src/vga_buffer.rs`,
`src/keyboard.rs`, `src/shell.rs`, `src/interrupts.rs` and `src/serial.rs`
— is just a function with no parameters, marked with `#[test_case]`, inside
a `#[cfg(test)] mod tests { ... }` block at the end of the file:

```rust
#[cfg(test)]
mod tests {
    use super::*;

    #[test_case]
    fn minha_verificacao() {
        assert_eq!(2 + 2, 4);
    }
}
```

The test passes if the function finishes normally, and fails if any
`assert!`/`assert_eq!` (or any other panic) fires inside it.
One single caveat: never write, inside an ordinary test like these, a
call that you know will panic on purpose (like the prompt's
`panic` command) — that would bring down the whole binary instead of
passing, for exactly the reason explained in the previous section. For that
specific case, the test needs to be its own file in `tests/`,
following the model of `tests/should_panic.rs`.

A new integration test is a new file inside `tests/`, with its
own minimal copy of the header that appears in
`tests/boot_integration.rs`:

```rust
#![no_std]
#![no_main]
#![feature(custom_test_frameworks)]
#![test_runner(os_rust::test_runner)]
#![reexport_test_harness_main = "test_main"]

use bootloader::{entry_point, BootInfo};
use core::panic::PanicInfo;

entry_point!(main);

fn main(boot_info: &'static BootInfo) -> ! {
    os_rust::init(boot_info);
    test_main();
    os_rust::panic::halt_loop();
}

#[panic_handler]
fn panic(info: &PanicInfo) -> ! {
    os_rust::test_panic_handler(info)
}

#[test_case]
fn meu_teste_de_integracao() {
    // ... the rest of the scenario under test
}
```

Each file in `tests/` boots the kernel from scratch, in its own QEMU
process — that is why `os_rust::init(boot_info)` needs to be called
again in each one, even if the previous test already called it in its
own binary. Since Milestone 3, `init` receives the `boot_info` that
`entry_point!` itself delivers (the memory map and the full physical
memory offset that memory initialization needs).

## Physical memory: the map the bootloader hands over

Until here, everything the kernel has used — the screen, the keyboard, the serial port — are
fixed addresses known in advance. Memory is different: how much RAM
the machine has, and which pieces of it are already occupied (by the kernel
itself, by page tables, by devices), only the bootloader can
tell, because it is the one that talks to the BIOS to find that out before
our code even starts running.

That is why the `bootloader` crate delivers, along with the `entry_point!`
call, a `BootInfo` structure with a `memory_map`: a list of
physical memory regions, each with a start, an end, and a type —
`Usable` (free, the kernel may use it), `Kernel`, `PageTable`, `Reserved`,
and others. The `memory_map` is read-only: the kernel never writes to it, it only
consults it. `src/memory.rs` uses exactly that list, and only it, to know
what it can hand out as free memory — never a guess, never an
assumption about the size of the RAM.

## Frames and pages: the 4 KiB blocks on both sides

Physical memory is divided into 4 KiB blocks called **frames**; the
address space the processor sees (*virtual* memory) is
divided into the same 4 KiB, called **pages**. A frame is identified
only by the physical address where it starts; a page, by the virtual address.
The central idea of virtual memory is that each page can be mapped
to any frame — or to none — and it is the processor, consulting a
structure called a page table, that does this translation on every memory
access, transparently to the code, which only sees virtual
addresses.

`src/memory.rs` defines `BootInfoFrameAllocator`: it walks the
`Usable` regions of the `memory_map`, breaks each one into 4 KiB frames, and hands out a
new frame on each call to `allocate_frame()` — never repeating one already
handed out, and returning `None` when the usable memory runs out (that is
all the `Option` type already guarantees: there is no "invalid frame"
disguised as a valid frame). Returning frames to the allocator is not something
this milestone needs to do: the only consumer is the heap, set up a single
time at boot.

## The 4-level page table, and how the kernel manages to edit it

On `x86_64`, translating a virtual address to a physical one goes through
four levels of tables (nicknamed P4, P3, P2, and P1), each with
512 entries — each entry points to the table of the next level, until the
last one (P1) points to the actual physical frame. The processor knows where
the active P4 is because its physical address is kept in a
special register, `CR3`.

But reading or editing these tables requires accessing the physical memory where
they live — and the kernel code only sees *virtual* addresses. This is where
the central piece of this milestone comes in: the `map_physical_memory` feature
of the `bootloader` crate (enabled in `Cargo.toml`) makes the bootloader map
**all** physical memory, at once, starting at a fixed virtual address
— the `physical_memory_offset`, also delivered inside the `BootInfo`.
So, to access the physical frame that starts at address `F`, just
add `F + physical_memory_offset` and use that result as an ordinary virtual
address. `active_level_4_table`, in `src/memory.rs`, uses exactly
that sum to reach the active P4 (read from `CR3`) and return a mutable
reference to it.

Instead of walking the four levels manually every time, the kernel uses
`OffsetPageTable`, a ready-made type from the `x86_64` crate that already knows how to do this
arithmetic — given the `physical_memory_offset` and the active P4, it offers
`translate_addr` (virtual address → physical, or `None` if the page has
no mapping — `memory::translate_addr`) and `map_to` (creates a new
mapping, creating any missing intermediate tables — used by
`memory::map_page`).

## How a new mapping is created

Mapping a new page to a free physical frame is: take a frame from the
`BootInfoFrameAllocator`, and call `map_to` on it, with the flags `PRESENT`
(the page exists) and `WRITABLE` (it can be written) — never
`USER_ACCESSIBLE` in this milestone, because ring 3 user programs only
arrive in Milestone 5. If the page already had a mapping, `map_to` returns an
explicit error (`PageAlreadyMapped`) instead of silently overwriting
what was already there — a mapping pointing to the wrong frame would be a
kind of bug that is very hard to trace later.

`memory::map_page` packs these steps into a single function, used both
by the integration tests (`tests/paging.rs`) and, indirectly,
by the heap setup that follows.

## The heap: why the kernel needs dynamic memory

Until this milestone, every kernel data structure had a fixed size,
known at compile time — the screen buffer, the scancode queue,
the prompt's line buffer. That works well when the maximum
size can be predicted in advance, but breaks as soon as the kernel needs something
whose size is only known at run time (for example, in Milestone 5, the
list of segments of an ELF executable, which varies from program to
program). That is exactly what a **heap** is for: a region of
memory from which the program can ask for variable-size blocks — the
`Box` (a single, allocated value) and `Vec` (a growing list) types from the
`alloc` crate of Rust's own standard library are the idiomatic way
to use this memory.

This kernel's heap is simple on purpose: a **fixed** range of 100 KiB
of virtual addresses, starting at `0x_4444_4444_0000` (an address
chosen only because it is far away from anything else the bootloader
has already mapped) — `src/allocator.rs`. At boot, `allocator::init_heap`
maps, one by one, all the pages of that range to free physical frames
(reusing exactly the `map_page`/`map_to` explained above) and only
then registers the global allocator. That order matters: no allocation
can happen before the whole heap is mapped.

## How the chosen heap allocator works

Registering a global allocator means telling the Rust compiler: "whenever
any code asks for `alloc`/`dealloc` — which `Box::new`, `Vec::push`, and
company do under the hood — call this function". `src/allocator.rs`
uses the `linked_list_allocator` crate for that, through the
`#[global_allocator]` attribute. The algorithm behind it is a linked list of
free blocks: each freed block (when a `Box`/`Vec` goes out of scope)
goes back to that list, available for the next allocation that fits in it
— **even if other blocks are still in use**, which is precisely
what lets the `mem` command be typed 100 times in a row without ever
exhausting memory: each `Box`/`Vec` it creates is returned at the end of the
same run of the command.

This milestone chose to use a ready-made crate for this algorithm, instead of
writing an allocator by hand, because the didactic goal here is to understand
physical memory and paging — the internal algorithm of a heap allocator
(free lists, fixed-size blocks, and the various ways of optimizing them)
is a subject in itself, which does not need to compete for this
milestone's lesson time.

And what if an allocation request does not fit in any free space in the heap? The
compiler calls the function marked with `#[alloc_error_handler]`, also in
`src/allocator.rs` — which here simply calls `panic!` reporting the
requested size and alignment, reusing the same readable panic screen
(and the same line on the serial port) that has existed since Milestone 0. An
exhausted heap never silently hangs the system nor returns invalid
memory — it stops in a way that can be read and understood.

## What the `mem` command is showing

`mem` (in `src/shell.rs`) is the on-screen proof of all this working
together:

```text
os-rust> mem
memoria fisica utilizavel: 123848 KiB
heap: 0x444444440000, 100 KiB
Box: valor=42, endereco=0x444444440000
Vec: tamanho=10, capacidade=16, soma=55
os-rust>
```

The first line sums all the `Usable` regions of the bootloader's `memory_map`
(`memory::info()`) — it is not the machine's total RAM, it is only the
part left free after what the bootloader and the BIOS itself already
reserved. The second shows where the heap is and how large, described
above. The last two actually allocate a `Box` and a `Vec` — the `Box`'s
address falls inside the heap range (often right at its start,
since it is the first allocation after boot), and the `Vec` starts empty
(`Vec::new()`) and grows with each `push`, so its final capacity may
be larger than its size (the growth strategy of the standard library's `Vec`
doubles the capacity when it runs out, instead of
reallocating on every element).

## CPU exceptions: when the processor itself interrupts the code

Since Milestone 1, the kernel already deals with **interrupts**: asynchronous
external events, such as a key being pressed (IRQ1) — something that can happen
at any moment, unrelated to the instruction that was running.
**Exceptions** are similar (they use the same table, the IDT, and the same
hardware mechanism to divert execution), but they are **synchronous**: the
processor itself triggers them, in the middle of executing a
specific instruction, because that instruction tried to do something it cannot —
access an unmapped memory page, execute an opcode that does not
exist, violate a protection rule. Each exception has a fixed vector in the
IDT (the first 32, reserved by the architecture — that is why hardware
IRQs start at vector 32, as Milestone 1 already explained) and,
for some of them, the processor pushes a 64-bit **error code**
with details about what went wrong, even before calling the
handler.

Until this milestone, the kernel only handled two: breakpoint (`#BP`, vector 3,
triggered by the `int3` instruction) and double fault (`#DF`, vector 8). All
the other exceptions — including page fault and invalid instruction — had
no handler at all. And that is exactly where the problem this
milestone solves lives.

## What happened without a handler: cascading double fault, then triple fault

When the processor tries to deliver an exception and the corresponding
IDT entry is empty (or, worse, when the delivery of the
exception itself fails for some other reason, such as an invalid stack), it does not
give up — it triggers a second exception, the **double fault** (`#DF`),
giving the kernel one last chance to react. A stack overflow is
exactly this case: the instruction that tries to push one more frame
onto an already full stack causes a page fault (the next stack position
has no valid page underneath) — and, since that page fault's own
handler *also* needs stack space to run, and there is none left, the processor cannot even
deliver the page fault handler. That becomes a double fault.

But until this milestone, the double fault also ran on the *same* stack (the
kernel's) — and if it was already exhausted, trying to deliver the double
fault *handler* also failed. When that happens inside a double
fault, the processor has nowhere left to escalate: it triggers a
**triple fault**, which no operating system handles — it is treated by the
hardware itself as "the system is unrecoverable", and the default reaction
of any real PC (and of QEMU, simulating one) is to reboot the machine
immediately, with no message at all. That is exactly the silent reboot
that anyone who worked with this project before this milestone knows.

## The GDT: why it still exists in 64-bit mode

The **GDT** (*Global Descriptor Table*) is a piece inherited from 32-bit
protected mode, where it defined memory segments with their own bases,
limits, and permissions — *segmentation*. In long mode (64-bit),
data segmentation is essentially turned off: every address is already
treated as if it started at zero. But the GDT still exists, because
the processor still requires a valid code segment selector in the
`CS` register, and it is where the **TSS descriptor** (below) has to
live — the `ltr` instruction (*load task register*), which activates the TSS, only
knows how to load a selector pointing to a GDT entry.

This milestone creates `src/gdt.rs` with a kernel-specific GDT, containing only
two entries: the kernel code segment (`Descriptor::kernel_code_segment()`,
used to reload `CS`) and the TSS descriptor
(`Descriptor::tss_segment(&TSS)`). User segments (ring 3) are left
for Milestone 5, when user mode requires its own code segment and data
segment to run programs outside the kernel (which is what happened:
see the "Milestone 5" chapter at the end of this text, where the GDT gains four
more descriptors).

## The TSS and the Interrupt Stack Table: the stack that solves the problem

The **TSS** (*Task State Segment*), in 64-bit mode, is no longer used to
switch tasks (as it was in 32-bit) — only one purpose remains:
holding stacks that the processor switches to automatically in certain
situations. One of these is the **Interrupt Stack Table** (IST): up to seven
stack pointers, each of which can be associated with a specific
IDT entry. When that association exists, the processor switches
to that stack *before* calling the handler — regardless of
which stack was in use at the moment of the fault.

`src/gdt.rs` reserves a static 20 KiB region
(`DOUBLE_FAULT_STACK`, five 4 KiB pages — generous slack over what the
handler really needs: just format and write a text message,
without allocating anything from the heap) and stores the address of its **end** (the
stack grows downward) in IST entry 0, inside the TSS. The IDT then
associates that entry with the double fault:

```rust
unsafe {
    idt.double_fault
        .set_handler_fn(double_fault_handler)
        .set_stack_index(gdt::DOUBLE_FAULT_IST_INDEX);
}
```

With this, even if the kernel's stack is completely blown
when the double fault happens, the processor switches to that
reserved, intact stack before entering the handler — the handler manages to
run, format the message, and write it (screen and serial) normally. That is
exactly the "before and after the reboot": without the IST, stack overflow =
triple fault = silent restart; with it, stack overflow = a readable
`#DF` screen, kernel halted in a controlled way.

## The fatal exception screen: one function, four exceptions

`#UD` (invalid instruction), `#GP` (general protection), `#PF` (page fault), and
`#DF` (double fault) are treated as **fatal**: the kernel does not yet
know how to run user programs (that only arrives in Milestone 5), so there is no
"just end the guilty program" — the only response would be to keep
running a kernel that has just proven it is in an
unexpected state. All four share a single private function,
`fatal_exception`, in `src/interrupts.rs`: it writes the name and abbreviation of the
exception, the address of the instruction that failed, the error code (when the
exception has one), and the os-rust version — all mirrored on the screen and on the
serial port — and ends by halting the CPU (`halt_loop`, the same `hlt` loop
already used by the panic screen since Milestone 0). Breakpoint (`#BP`)
remains the only non-fatal exception: the screen gets just a short line, and
control returns to the prompt normally.

## How to read the error code and the address of a page fault

Page fault is the only one of this milestone's five exceptions that carries
enough extra information to be worth translating into words. The
processor pushes a 64-bit error code (`PageFaultErrorCode`,
a set of *bit flags*) and stores, in the `CR2` register, the exact
virtual address that caused the fault — `fatal_exception` reads both and builds
a message like this one (screen and serial have the same content):

```text
[EXCEPTION] Page Fault (#PF) - os-rust v0.4.1 parou
endereco da instrucao: 0x...
codigo de erro: 0x0
endereco de falha: 0x444444459000
acesso: leitura
causa: pagina ausente
os-rust v0.4.1
```

Two bits of the error code are enough for the interpretation in words: the
`CAUSED_BY_WRITE` bit distinguishes read from write, and the
`PROTECTION_VIOLATION` bit distinguishes "page absent" (there was no mapping
at all there) from "protection violation" (there was a mapping, but the access
did not respect its flags — for example, writing to a read-only
page). The prompt's `falha pagina` command triggers exactly that
scenario on purpose: it reads a byte from the address right after the last mapped
heap page (`allocator::HEAP_START + allocator::HEAP_SIZE`) — an
address that Milestone 3 never maps, so the page fault is guaranteed and
predictable.

## The `falha <tipo>` command: triggering each exception on purpose

`src/shell.rs` gains the `falha <tipo>` command, with five types, each one
triggering its exception in the simplest way possible to explain:

- `falha pagina` — a read at a never-mapped address (above).
- `falha pilha` — a recursive function with no base case. Alone, that
  recursion would become an infinite loop without ever overflowing the stack, because the
  compiler would optimize the recursive tail call (*tail call*) into
  a `jmp` that reuses the same frame; a volatile read
  (`volatile::Volatile::new(0u8).read()`) after the recursive call
  prevents that optimization, forcing each call to actually push.
- `falha opcode` — the `ud2` instruction, reserved by the Intel/AMD manual itself
  as always invalid, with no tricks needed.
- `falha protecao` — writes to a *non-canonical* virtual address: in
  long mode, bits 63 to 47 of every 64-bit address must be
  all equal (a sign extension of bit 47); the address
  `0x8000_0000_0000_0000` violates this rule on purpose (bit 63 set,
  bit 47 clear), which the processor rejects as `#GP` before even
  checking whether the page exists.
- `falha breakpoint` — the `int3` instruction, the same non-fatal exception that
  Milestone 1 already demonstrated.

With no argument, or with a type that is none of these five, the command
lists the available types instead of triggering anything.

## How the name and version get from `Cargo.toml` to the screen

A smaller request, but visible in every lesson: the system's name and version
need to appear in its messages. The technique is entirely at compile
time, with no formatting code at run time:
`env!("CARGO_PKG_NAME")` and `env!("CARGO_PKG_VERSION")` are macros of
`cargo`/`rustc` itself that expand to string literals with the
values of the `name`/`version` fields of `Cargo.toml` — and `concat!` joins
those strings into a single constant, in `src/lib.rs`:

```rust
pub const NAME: &str = env!("CARGO_PKG_NAME");
pub const VERSION: &str = concat!(env!("CARGO_PKG_NAME"), " v", env!("CARGO_PKG_VERSION"));
```

Since they are all macros resolved by the compiler, `NAME`/`VERSION` are already
born as complete strings (`"os-rust"`/`"os-rust v0.4.1"`) inside the
compiled binary — there is no file reading, no allocation, and
there is no other place in the code where the name or version appear
written by hand. Every place that needs to show one of the two — the welcome
message (`print_welcome`, called by `main.rs`), the first
serial diagnostic line, the prompt (`shell::PROMPT`), the `sobre`
command, the panic screen, and the fatal exception screen — only reads
`crate::NAME`/`crate::VERSION`. Changing the name or version thus becomes a
change in a single place: the `name`/`version` fields of `Cargo.toml`.

## Milestone 4.1: why renaming a project touches more places than it seems

Milestone 4.1 changed the project name from `proto-os` to `os-rust`. In an ordinary
language, "renaming a project" would be just editing some text. In
Rust, a package name becomes, on its own, several different
names in different places — it is worth understanding why.

**Why the package `os-rust` becomes the crate `os_rust`.** The `name` field of
`Cargo.toml` can have a hyphen (`"os-rust"`), because there it is just text
inside a TOML file. But a Rust code identifier (the name
that appears after `use` or before `::`) can never have a hyphen — the
language grammar does not allow it. So Cargo automatically replaces
each `-` with `_` when generating the *crate* name (the compilation
unit): the package `os-rust` compiles to the crate `os_rust`, and it is
`os_rust::something` that appears in every `use` of the project (`src/main.rs`,
each file in `tests/`). The two spellings coexist on purpose: the
manifest uses the "pretty" spelling, the code uses the spelling that compiles.
But there is a third spelling, which does not go through that replacement: the macro
`env!("CARGO_PKG_NAME")` (used in the previous section) expands to the
**literal** text of the manifest's `name` field — with the hyphen preserved. That is
why `NAME`/`PROMPT`, although they live inside Rust code, show
`"os-rust"` (with a hyphen) on the screen, and not `"os_rust"`.

**Why the target file name decides the folder name inside
`target/`.** The file `x86_64-os_rust.json` (renamed from
`x86_64-proto_os.json` in this milestone) describes, to `rustc`, what the
destination CPU/platform is like — there is no "official" Rust
`x86_64-os_rust` target, so this project defines its own, with
`json-target-spec` enabled in `.cargo/config.toml`. Cargo uses the
**file name** (without the `.json` extension) as the identifier of that
target, and creates a subfolder with that same name inside `target/` to
hold everything compiled for it — hence `target/x86_64-os_rust/`.
Renaming just the file (touching nothing else) would already be enough for
Cargo to start using the new subfolder; an old folder
`target/x86_64-proto_os/`, if left over from a previous build, simply
becomes orphaned, getting in the way of nothing.

**Why `█` in UTF-8 is not the same as byte `0xDB` of code
page 437.** The new logo (`src/logo.txt`, shown on screen by
`vga_buffer::draw_logo`) uses the `█` character (full block) in the symbol's
lines. The source file is UTF-8, today's universal standard, in which each
character can occupy from 1 to 4 bytes — `█` specifically occupies 3 bytes
(`0xE2 0x96 0x88`). But the VGA text hardware (the same `0xb8000`
explained above) does not understand UTF-8: each screen position is *one*
character byte plus one color byte, using a table of 256 fixed symbols
called "code page 437" (the same one inherited from the original PC of
the 1980s), in which position `0xDB` is precisely a full block — a
different symbol from Unicode's `█`, but visually identical. If the
kernel wrote the 3 UTF-8 bytes of `█` straight to the screen (as the normal
`Writer` does with ordinary text), three wrong symbols would appear
side by side, not a single block. That is why `draw_logo` does not use the normal
`Writer`: it reads the logo **Unicode character by Unicode character**
(`str::chars()`, not `str::bytes()`) and translates each `'█'` to the single
byte `0xDB`, writing straight into the VGA buffer cells.


## Milestone 5: the first user program

Until Milestone 4.1, os-rust only executed code from the kernel itself. Milestone 5
does the thing that gives meaning to everything else: it executes a program written
**outside** the kernel, at a lower privilege level, which can only
write to the screen by asking the kernel. You see it by typing `run hello` at the
prompt. This chapter explains the whole path, in the order in which the pieces
come into action.

### Why the program is compiled separately

The kernel is a `no_std` binary for the `x86_64-os_rust.json` target, with
details that only make sense inside the kernel (for example, the
`code-model = kernel` and the stack red zone turned off, because an
interrupt can arrive at any moment on top of the kernel's stack). A user
program is something else: it runs in ring 3, at low addresses, on a stack
that the kernel never uses. That is why it has **its own target**,
`x86_64-os_rust_user.json`, and its own crate, `programs/`, with one
executable per file in `programs/src/bin/` (`hello.rs`, `crash.rs`).

A detail that shows up when choosing where the program will live: the
linker script `programs/link.ld` fixes the base at `0x4000_0000` (1 GiB).
It looks arbitrary, but it is not: Rust's default code model generates
signed 32-bit absolute addresses, so the program needs to fit
below 2 GiB. In an attempt with a much higher base the linker failed
with `relocation R_X86_64_32 out of range`. Each group of sections (`.text`,
`.rodata`, `.data`) starts on its own 4 KiB page, so that the
loader can give different permissions to each one.

### How the executable gets inside the kernel

The kernel does not compile anything while it runs: it is an already built binary. So the
program needs to be **inside** it. This is done at build
time, with no manual step, by a `build.rs` at the root of the
repository (a *build script*: a Rust program that Cargo runs before
compiling the package). That script:

1. runs a second `cargo build`, with the user target, inside
   `programs/`;
2. copies each resulting ELF to the build output folder (`OUT_DIR`);
3. writes, also in `OUT_DIR`, a `programs.rs` file with a table
   (program name + the bytes, via `include_bytes!`), which
   `src/programs.rs` includes with `include!`.

The same mechanism that already embeds `src/logo.txt` as text now
embeds a compiled binary. `rerun-if-changed` makes Cargo redo everything
whenever anything in `programs/` changes: that is why the embedded `hello` is never
out of date, and does not need `cargo clean`.

Running a `cargo` inside a build script has three pitfalls, all
solved in `build.rs` and commented there: the inner `cargo` uses its own
`--target-dir` (the outer one holds the build directory *lock*, and
waiting for it would be waiting forever); the environment that the outer `cargo`
injects (flags, target, profile) is erased, so the user program
does not inherit the kernel's options; and `programs` needs to be a member of the
*workspace* declared in `Cargo.toml` (`default-members = ["."]` keeps
`cargo run` and `cargo test` compiling only the kernel).

If the program does not compile, `build.rs` ends with `panic!` **before** copying
any file: `cargo run` stops with the compiler error in
view, and a boot image with an old program by mistake never comes out.

### What an ELF is and what the loader reads

The file that the inner `cargo` produces is an **ELF64**: the executable format
of Unix systems. It starts with a 64-byte header
(the "magic" `7f 45 4c 46`, whether it is 32 or 64 bits, for which CPU, where the
first instruction is) and a table of **program headers**, which say what
to copy where. Each `PT_LOAD` describes a piece of the program: a virtual
address, how many bytes to copy from the file, how many bytes it occupies
in memory (what goes beyond the file is zeroed: the `.bss`) and whether it is readable,
writable, executable.

`src/elf.rs` reads these fields with `from_le_bytes`, without any crate, and
refuses, before mapping anything, everything that is not a static ELF64
for x86-64, or whose segments leave the user region,
split a page, or have the entry point outside executable code. Then,
`src/user.rs` does the work: for each page of each segment, it takes a
physical frame, zeroes it, copies the bytes, and maps it with the segment's
permissions. A code page is born without the write bit, and a data or
stack page is born with the `NO_EXECUTE` bit: no page is both
writable and executable at the same time (the **W^X** rule). The kernel writes to the
frames through the window of the full physical memory map, and not through the user
address, so it can fill a page that will end up read-only.

### Protection rings and the GDT with user segments

x86 has four privilege *rings*; modern systems only use two:
**ring 0** (the kernel, which can do everything) and **ring 3** (programs, which cannot
touch hardware or kernel memory). The current ring is the privilege
level of the code selector loaded in `CS`. That is why the GDT
(previous chapter) gains, in Milestone 5, four descriptors: kernel data,
user data, and user code (in addition to the kernel code and the
TSS that already existed). The order is imposed by the hardware: user data
must come **before** user code, and kernel data right
**after** kernel code, because the syscall entry and exit instructions
compute the selector of one from the other (`STAR + 8`,
`STAR + 16`). The `x86_64` crate checks this layout when the kernel
writes the `STAR` register.

### The `syscall` instruction

A user program cannot call a kernel function: the kernel is
in another ring. The way to ask for a service is the `syscall` instruction: the CPU
goes up to ring 0 and jumps to an address that the kernel registered beforehand,
in the `LSTAR` register. Four registers configure the mechanism
(`src/syscall.rs`):

- `EFER.SCE`: turns the instruction on;
- `STAR`: the kernel and user segment selectors;
- `LSTAR`: the address of the entry stub (`syscall_entry`);
- `SFMASK`: the flags that the CPU clears by itself on entry (interrupts,
  direction, *trace*).

The convention (documented in `SYSCALLS.md`) is: syscall number in `rax`,
arguments in `rdi`, `rsi`, `rdx`, result in `rax`. The instruction destroys
`rcx` (where the CPU keeps the return address) and `r11` (where it keeps
the flags), and the contract tells the program to treat both as destroyed; the
kernel preserves everything else.

There is a catch: the `syscall` instruction, unlike an exception, **does not
switch stacks**. On arriving at the kernel, `rsp` still points to the program's
stack, which the kernel must never use (the program could have put any
value there). That is why the assembly stub saves the program's `rsp`
in a safe place and switches by hand to the kernel stack (the same one that the TSS
declares in `rsp0`, used by the processor when an *exception* arrives in
ring 3), pushes the program's state (since Milestone 7, an entire `TaskContext`,
with the 15 registers and the return frame), calls the dispatcher in
Rust and returns with `iretq`. (Until Milestone 6 the stub pushed only the registers
that the contract promises to preserve and returned with `sysretq`; `iretq` allows
returning also a program that was taken off the CPU in the middle, see the
Milestone 7 chapter.)

### How the program returns to the prompt

The `run` command is an ordinary kernel function, called by the prompt loop.
How does it "wait" for a program that runs in another ring? With the same trick as
C's `setjmp`/`longjmp`. `enter_user` (assembly) pushes the registers
that the kernel needs to preserve, saves the kernel's `rsp`, and enters the
scheduler, which puts the program in ring 3 (the initial context zeroes all
registers: nothing from the kernel can leak into the program). When the program
calls `exit`, or does something wrong, the kernel is on an entry stack, inside
a handler; when the last program ends, `leave_user` restores the saved
`rsp`, pops the registers, and executes `ret`, which returns to whoever
called `enter_user`, as if it had finished normally. Before that, the
scheduler destroyed the program's address space and returned the frames
to the allocator: running `hello` a thousand times does not exhaust memory. What shows the
result on the screen is the `run` command, in a single place (in Milestone 7, at the moment
each program ends).

### Why the kernel does not trust the `write` pointer

`write(ptr, len)` receives an address and a size that **the program**
chose. If the kernel read `ptr` without looking, a program could ask
to "write" an address of the kernel itself and see (or cause)
whatever it wanted. That is why `sys_write` checks, before reading any byte,
that the whole range is inside the user region and that **each
page** of it is mapped and marked as user-accessible; if not, the
call returns `ERR_FAULT` (`-1`) without writing anything, and the program
keeps running. That is the exact point at which the kernel protects itself from the
program.

### Why `#DE`, `#SS`, and `#NP` needed a handler

A CPU exception in a user program cannot bring down the kernel.
The Milestone 4 handlers (`#UD`, `#GP`, `#PF`) now look at which ring the
exception came from (the code selector pushed by the CPU): in ring 3, only the
program is ended, with a readable message; in ring 0 they remain
fatal, as before. But that was not enough. A missing gate in the IDT does not
become an ordinary error: the processor raises another exception, without a handler,
and escalates to **double fault**. It was confirmed in the test: with the
divide-by-zero gate (`#DE`) removed on purpose, the divide-by-zero
test ended in `Double Fault (#DF)`, which is fatal for the kernel. That is why
`#DE`, `#SS`, and `#NP` also gained a handler. (A QEMU curiosity: a
`push` with a non-canonical `rsp` arrives as `#PF`, and not as `#SS`, which is
what a real processor would raise; the test accepts both.)

### A detail about the `USER_ACCESSIBLE` bit

For a page to be accessible in ring 3, the `USER_ACCESSIBLE` bit must
be set at **all** levels of the page table, not just on the final
page. The user region sits within the same level-4 entry
(number 0) that the kernel uses, so mapping the user's first page
sets that bit on that entry too. This does not expose the kernel: the
kernel's pages sit under another level-3 entry (the kernel lives in the
first MiB, the program from 1 GiB on) and their page entries
do not have the bit, so the processor keeps barring any ring 3
access to them. It is the combination of all levels that decides.

## Milestone 6: the programming interface

In Milestone 5, `hello` asked the kernel for everything with the `syscall` instruction written by
hand. That proves the mechanism works, but nobody writes a program
like that. Milestone 6 turns the mechanism into a **programming interface**:
a library (`runtime/`) that hides the instruction, two new syscalls
(read a line from the keyboard and ask for memory) and the guarantee, now demonstrated
with a purpose-built program, that an error in the program never brings down the
kernel. You see it all by typing `run eco` and `run falha_memoria` at the prompt.
Anyone who wants to write their own program, without understanding any of this
inside, reads `GUIA_DO_PROGRAMADOR.md`; here is what happens underneath.

### A runtime library: the equivalent of libc

A user program has no standard library: no `println!`, no `Box`,
not even a `main`. The `runtime/` crate gives it that, and it is what libc is
for a C program. It has four files:

- `sys.rs`: the **only** place with the `syscall` `asm!`. It is the same `asm!` that
  Milestone 5's `hello` had written by hand, now written only once, with a thin
  wrapper per syscall (`write`, `exit`, `read_line_raw`, `alloc`).
- `io.rs`: `print!` and `println!` (which do `write`) and `read_line`.
- `heap.rs`: the global allocator, which makes `Box`, `Vec`, and `String` work.
- `lib.rs`: the `entry!` macro and the `panic!` handler.

The syscall numbers are not written twice: they live in a tiny crate,
`abi/`, on which **both the kernel and the library** depend. This way the
two sides never diverge (the kernel test that compares `SYSCALLS.md` with
the constants protects the library too).

### `_start` and the `entry!` macro

The processor starts executing the program at the address that the ELF calls the
entry point, `_start`. A Rust `main` is not that: someone needs to
set the stage, call `main` and, when it returns, call `exit`. That
is what the `entry!(main)` macro generates **inside the program**: a
`_start` function that calls `main`, takes the `i32` it returns, and passes it to `exit`.
Since the macro calls `main` with the signature as written, the compiler checks that
`main` is `fn() -> i32`; a `main` of another type does not compile. A program
never returns from `_start`: there is nowhere to return to, so the last step is
always `exit` (it is the rule of the contract, section 3 of `SYSCALLS.md`).

### `print!` and what each `println!` does

`print!` writes with `core::fmt::Write` over the `write` syscall. The
`format_args!` produces the text in several pieces (`println!("a {}", 1)` generates
`a `, `1`, and `\n`); the library joins them into a 256-byte buffer on the
program's stack and hands everything to the kernel in a **single** `write` call. In Milestone 6
each piece was one call, and that was simple and sufficed; with several
programs at the same time (Milestone 7), three calls per line let a task switch
split the line in the middle (`ping ` from one program, `pong 1` from another).
One call per line solves it: each `write` reaches the screen whole.

### `read_line`: waiting for a key inside a syscall

`read_line(&mut buffer)` makes the `SYS_READ_LINE` syscall, which **blocks** the
program until the person presses Enter. While waiting, the kernel shows on the
screen what is typed and erases with Backspace (`write` does not know how to erase, so
that editing has to be done by the kernel). The curious part is how the kernel waits.

How the kernel waits changed in Milestone 7. In Milestone 6, the wait happened
**inside** the syscall: the `syscall` instruction enters with interrupts
off (that is `SFMASK`), so the kernel executed `sti; hlt` until IRQ1
brought a key, the only exception to the rule "syscall runs with interrupts
off". That only works with one program at a time: while one
program sleeps inside the syscall, no other runs. Now the task is
**blocked** and the scheduler hands the CPU to another (see "The keyboard with several
programs", in the Milestone 7 chapter), and no syscall turns interrupts on.
`keyboard::read_line` still exists as the blocking read of a single
reader (the tests use it); what it and the scheduler share is the line
assembler, `LineEditor`.

Whose is the keyboard while the program runs? The program's. The loop that reads the
keyboard and feeds the prompt (`shell::poll_keyboard`) is **stopped inside**
`run`, waiting for the last program to finish; whoever reads the queue is the scheduler,
at a program's request. When the last one ends, the loop continues, and whatever
is left in the queue (type-ahead) goes to the prompt, losing nothing.

### The heap that only grows: `SYS_ALLOC`

`Box` and `Vec` need an allocator, and the allocator needs memory. The
kernel has a fixed heap, mapped at boot; a program starts **without a heap**.
`SYS_ALLOC(size)` expands the program's heap: it rounds up to 4 KiB pages,
maps new pages (zeroed, writable, never executable) right
after the ones it already has and returns the address of the start of the new area.
It is Unix's `brk`. The heap lives in a fixed window, `[0x6000_0000,
0x6010_0000)`, so at most 1 MiB fits; going beyond returns `ERR_NOMEM`
instead of hanging anyone, and the call is all or nothing. The page right after
the end of the window is never mapped: writing past the end of the heap is a
`#PF`, not a silent corruption.

The library allocator (`heap.rs`) is the same `linked_list_allocator` as the
kernel's: only where the memory comes from changes. When allocation fails, it asks for more
pages with `SYS_ALLOC` (at least 16 KiB, so as not to make a syscall for every
small `Box`) and **extends** the same block, because the contract guarantees that
each new area starts where the previous one ended. At the end of the program
(`exit`, fault, or invalid syscall) the heap goes back to the frame allocator along
with the code and the stack: running a 1 MiB program 150 times, more than the
QEMU's memory, exhausts nothing, and a test proves it.

### Why a program fault does not bring down the kernel: `falha_memoria`

`falha_memoria` writes to address `0xdead_beef`, which is not its own. The CPU
raises a `#PF` in ring 3. The `#PF` handler looks at which ring the exception
came from (`came_from_user`, the code selector the CPU pushed): in ring 3,
it records the reason, ends only the program, and returns control to the prompt, which
shows `encerrado por erro de memoria` with the fault address
(`0xdeadbeef`) and the error code (`0x6`: came from ring 3, was a write, the
page did not exist). In ring 0 the same `#PF` remains fatal, with the exception
screen of Milestone 4. It is the same rule as Milestone 5, now with a program made
to show it: the kernel stays up, and the next program (`run hello`,
`run eco`) runs normally.

### A bug that only showed up with the key wait

On running `run eco` for real in QEMU, the screen filled with garbage as soon as the
first key arrived, even though all the automated tests passed. What
was wrong was the kernel's entry stack: a `static` of `[u8; N]`
has alignment 1, so the stack address (and the top, which is what the
processor and the `syscall` stub use) could land on any byte; the top
was at `0x...f3`. The `syscall` stub assumes a top that is a multiple of 16 (which is what
the calling convention requires), and nothing had shown up before because no
syscall waited with interrupts arriving on top of that stack.
Declaring both stacks with `#[repr(align(16))]` fixed it, and there is a test that
checks the alignment. Automated tests do not catch everything: QEMU
with a real keyboard remains part of the validation.

## Milestone 7: multitasking

Until Milestone 6, the kernel ran one user program at a time: `run` occupied the
prompt until the program finished. Milestone 7 loads **several** at the same time and
alternates the CPU among them, first when the program asks (the **cooperative**
switch, the `SYS_YIELD` syscall) and then when the timer commands (the
**preemptive** switch). The central idea fits in one sentence: every switch happens when a
program enters the kernel, and at that moment the kernel is in the middle of nothing.

### What an execution context is

To take a program off the CPU and give it back later "exactly where it stopped",
the kernel needs to save everything that defines its state in ring 3: the 15
general-purpose registers, the instruction pointer (`rip`), the stack (`rsp`),
the flags (`rflags`), and the segment selectors (`cs`, `ss`). That is a
`TaskContext` (`src/task.rs`): 20 64-bit words, in an order chosen on
purpose. The last five fields (`rip, cs, rflags, rsp, ss`) are
**exactly** the frame that the `iretq` instruction consumes; the first 15
(`r15` at the lowest address, `rax` at the highest) are the registers, in the order in which
the assembly pushes them, `rax` first and `r15` last.

This makes the context a block that can be assembled in two places with no copying
at all. The `syscall` stub (`syscall.rs`) pushes the five frame fields and
then the 15 registers, and when the CPU enters through a timer interrupt
it pushes the frame itself, and the stub (`timer.rs`) pushes the 15. In both cases the
kernel's entry stack comes to contain a `TaskContext`, and the Rust code
receives a `&mut TaskContext` pointing straight at it. Resuming a program is the
reverse path, in `resume_task` (`user.rs`): point `rsp` at a
`TaskContext`, pop the 15 registers, and execute `iretq`, which loads
`rip, cs, rflags, rsp, ss` all at once and enters ring 3. A program's first entry
uses the same path: the initial context (`TaskContext::initial`)
has `rip` at the ELF entry, `rsp` at the top of the stack, `IF` set, and `rcx` and
`r11` with the initial `rip` and flags (it was an effect of `sysretq`; now it is
the kernel that puts them there).

### Why there is no per-task kernel stack

The classic design gives each task a kernel stack and a
`switch_to` routine that swaps stacks in the middle of Rust code. Here it is not needed: every
switch happens at a ring 3 → ring 0 boundary (a syscall, an exception, or the
timer), when the kernel's entry stack has just been loaded and **is
empty**, and the program's state is whole at the top of it. The kernel is
"run to completion" on each entry: there is nothing of it to save between two
switches. Switching is copying that `TaskContext` to the `Task` that leaves and loading
another's. It is the reason the whole scheduler fits in ~270 lines.

One consequence: the return from a syscall went from `sysretq` to `iretq`. `sysretq`
only returns `rip` and `rflags` through `rcx` and `r11`, and does not know how to restore
a preempted program in full; `iretq` does. The contract still
says that `rcx` and `r11` are destroyed by a syscall, but the kernel
now returns them intact.

### The cooperative switch: `SYS_YIELD`, step by step

1. The program executes `syscall` with `rax = 5`. The stub (`syscall_entry`) switches
   to the kernel's entry stack and assembles the `TaskContext`.
2. `syscall_dispatch` receives the context and calls `scheduler::yield_now`, which
   writes `0` to `rax` (the result of `yield`).
3. If there is no other ready task, `yield_now` simply returns: the stub
   pops the context and goes back to the same program. If there is, it copies the context to
   the current `Task`, marks it `Ready`, and calls `run_next`.
4. `run_next` is the single point through which every task starts or resumes running. It
   chooses the **first `Ready` after the one that ran last**, in circular
   order (a round-robin: `ping`, `pong`, `ping`, ...), activates its
   address space (`CR3`) and calls `resume_task`.
5. `resume_task` pops the other task's context and executes `iretq`: the
   other program continues at the instruction following its `syscall`.

The first `run_next` of a run does not come from a syscall: `enter_user`
saves the kernel state (like `setjmp`), turns off interrupts, and jumps to
the scheduler; when the last task ends, `leave_user` restores that state
and "returns" from `enter_user`, as if it had finished normally.

### One address space per program

The programs are all linked at `0x4000_0000`. If they shared a page
table, any one could read another's memory (and two could not even
coexist at the same address). That is why each task gets its **own P4
table** (`memory::AddressSpace`).

Creating a space is allocating two frames, one for the P4 and one for a P3, and
copying the kernel's tables into them. The entries of the copied P4 point to the
**same** lower-level tables, so the kernel, the physical memory
window, and the entry stack remain visible with any `CR3`; only the entry
for the user region points to its own P3, which is a copy of the kernel's with the
user-region entry **empty**. The program's pages are mapped
afterward, while the space is active, and `map_to` creates the P2 and P1 tables, which only
it uses. Switching tasks is writing `CR3` (which also flushes the TLB).

This solved a leak that existed by construction: `Mapper::unmap` does not
free page tables. Destroying a space (`AddressSpace::destroy`)
**walks** the user region (`P3[1] → P2 → P1`) and returns to the allocator each
page frame and each table frame, plus its own P3 and P4. Nothing belonging to the kernel
is touched. A test runs two programs 100 times and checks that the
count of frames in use returns to the same value.

### The timer: PIT and IRQ0 through the PIC

The PIT (Programmable Interval Timer) counts down from a divisor and generates an
interrupt on each round of the count. Its oscillator runs at 1,193,182 Hz;
with the divisor `11932` (the rounded division, `1,193,182 / 100`), that gives 100
interrupts per second, one *tick* every 10 ms. `timer::init` writes the
command `0x36` (channel 0, mode 3) to port `0x43` and the divisor, low byte and
high byte, to port `0x40`. The interrupt arrives through the **IRQ0** line of the 8259 PIC,
vector 32; the PIC mask, which only let IRQ1 (keyboard) through, now
also releases IRQ0.

Every hardware interrupt handler must finish with the **end of
interrupt** (EOI, writing `0x20` to port `0x20` of the master PIC); without it the
PIC never delivers the next tick. The timer stub sends the EOI **before** any
task switch, on all paths: the CPU does not return to the point where the
handler was if the scheduler switches tasks, and an EOI left for later would
silence IRQ0 forever. A test checks that, after many switches,
the tick counter keeps advancing.

### Why and where the preemptive switch is safe

The kernel is **never** switched. The timer stub (`timer_entry`) looks at the code
selector that the CPU pushed, and its RPL says where the interrupt came from:

- from **ring 0** (the kernel was running: the idle loop, the prompt, a test):
  it counts the tick, sends the EOI, and returns with `iretq`. It does not switch tasks, does not allocate,
  does not take any lock;
- from **ring 3** (a program was running): it pushes the 15 registers
  (a `TaskContext` is born), sends the EOI, and calls the scheduler, which decides whether to
  hand the CPU to another program.

This answers the question "at what point is it safe to switch tasks?". All the
rest of the kernel (syscalls, exceptions, program loading, the frame allocator,
the screen) runs with interrupts **off** (the `syscall` `SFMASK` and the
IDT interrupt gates do that), and so is never interrupted by the
timer. The only stretch with `IF = 1` is the idle wait (`hlt`), which holds
no lock. There are no critical regions to mark: the safe point is the
ring 3 → ring 0 boundary, and it is also the only place where switching happens. A tick that arrives
while the kernel handles a syscall stays **pending** on the CPU and is delivered as soon
as `iretq` returns the program to ring 3 with `IF = 1`.

A consequence of this rule is worth recording: the code that runs after an
entry from ring 3 (the scheduler, the termination of a task) **may** allocate
and free memory, because no kernel code was in the middle of an
operation, so no lock is held. Handlers fired in ring 0 remain
forbidden from allocating.

### The time slice, and what we learned from it

The first version switched tasks on every tick coming from ring 3 ("1-tick
slice"), and it broke a simple guarantee: `ping` and `pong` stopped alternating
always in the same order (sometimes `pong 1` came out before `ping 1`). The cause is the
combination of two things: the kernel runs with interrupts off, so a
tick that arrives during a syscall stays pending and is delivered the instant
the program runs again; and the PIC keeps **at most one** pending tick. A
tick fell between a program's write and its `yield`, and it lost its turn.

The fix is to count the slice. When putting a task on the CPU, the scheduler stores
the value of the tick counter (`slice_start`); a tick coming from ring 3 only takes
the CPU from the task if `ticks - slice_start >= SLICE_TICKS`, and `SLICE_TICKS` is **5**
(50 ms). Each return from a syscall may add a tick without the program having
computed anything, but a program that writes a line and yields the CPU makes two or
three syscalls at a time, fewer than 5: it never accumulates a slice with that alone. Only
a program that computes in ring 3 for 40 ms or more is interrupted, which is exactly what
`contador_a` and `contador_b` do. With 2 ticks the problem diminished but did not
vanish: `run ping trio` still came out of order in 2 of 3 runs on QEMU; with
5, it came out in order in 6 of 6.

### The keyboard with several programs

`SYS_READ_LINE` validates the pointer as before and, instead of waiting inside the
syscall, **blocks the task** (`WaitingKeyboard`) with a sequence number (the
`ticket`): the lowest number is the one that asked first. The scheduler hands the CPU to
another task.

Whoever looks at the keyboard is `scheduler::poll_keyboard`, and only while someone is
waiting: whatever nobody asked for stays in the queue, as in Milestone 6. It assembles the line
with the `LineEditor` for the task with the lowest `ticket` (echo and Backspace included);
when Enter completes the line, it is stored in the task, which becomes
`Ready`, and the following keys count for the next one waiting. A key never
goes to two programs, and a half-typed line remains the property of whoever asked
first, even if another program asks later. The **copy** of the line into the
program's memory only happens when it runs again (`deliver_line`), with
its address space already active: the pointer was validated before
blocking, and nothing unmaps the pages of a waiting task.

`poll_keyboard` runs when a task blocks (type-ahead), on every
`yield`, on every tick coming from ring 3, and on every turn of the idle loop. The tick
matters: with one program waiting for the keyboard and another just computing, the only
chance for the kernel to look at the queue is the tick; if `preempt` did not call
`poll_keyboard` **before** deciding whether there is another ready program, the line would only
arrive after the other one finished. A test covers exactly that.

When no task is ready but some are waiting, the kernel **sleeps**: the idle
loop of `run_next` executes `sti; hlt` (as one atomic instruction: a key
or a tick that arrives between looking and sleeping wakes the CPU), and each turn of the loop
is caused by an interrupt. There is no busy loop. The tests prove this
by counting idle turns against ticks, and to "type" in the middle of
execution they use a hook that the scheduler calls on each `poll_keyboard`.

### The life cycle of a task

1. `run_images` loads **all** the requested programs (each in a new space)
   before starting any; if one fails, those already loaded are destroyed and
   nothing runs. More than 4 programs, or a name that does not exist, refuses the whole
   request.
2. Tasks are born `Ready`, in the order they were requested.
3. A task ends through `exit`, through an exception in ring 3, or through a nonexistent
   syscall. In all cases the path is `terminate_current`: it returns to the kernel's
   address space, records the reason, **notifies the shell** (which
   shows the message right away, before the others finish), destroys the space
   (all frames go back to the allocator) and passes the CPU along.
4. When no task remains, `leave_user` returns control to the prompt.

That is why a fault in one program does not bring down the others either: the kernel only
discards the task that failed. The tests assemble the support programs by hand
(few-byte ELFs, with a mini-assembler in the test file), and one of them
checks that each register, the stack, and the heap of two alternating programs
come back exactly as they were.

### What was left out

Priorities, `sleep`, creating programs from other programs,
communication between programs, and synchronization (mutex, semaphore) remain
out of scope. The kernel is still single-processor and without an APIC.

## Milestone 8: file system

Until Milestone 7, every program traveled inside the kernel, and the only way for the
kernel to obtain data from outside was the program table built by `build.rs`. 
Milestone 8 gives os-rust the notion of a **file**: the kernel starts reading files,
always read-only, from two places, `/ram` (a ramdisk embedded in the
boot image) and `/disco` (an ATA disk), and executing a program read from
one of them. Both sources hold the same format, FAT16, and the same code reads
both. One question guides the whole chapter: *what if the bytes the kernel reads
are wrong?* A file on a disk is outside data, and outside data
is not trustworthy.

### A block device: the smallest idea of a "disk"

For the FAT reader, a disk is a sequence of 512-byte **sectors**
numbered from zero (the number is the logical block address, LBA), and the
only operation is "give me sector `n`". It is the `BlockDevice` trait (`src/blockdev.rs`),
with two functions: how many sectors the device has, and reading one. Two things
implement it:

- `RamDisk`: a slice of bytes that is already in memory (`include_bytes!` of the
  ramdisk image). Reading sector `n` is copying 512 bytes from there.
- `AtaDisk` (`src/ata.rs`): a real disk, which lives behind I/O
  ports (next section).

The FAT reader (`src/fat.rs`) only knows the trait. That is why `ls /ram` and `ls
/disco` go through the **same** code, and the reader's tests run on images
fabricated in memory with no hardware. There is no cache, no multi-sector reads,
and no writing: the milestone is read-only and what is read is little.

### The layout of a FAT16 volume

A FAT volume is made of four regions, in order:

```text
sector 0        boot sector (describes the volume; ends in 0x55 0xAA)
sectors 1..35   allocation table (FAT), two copies of 17 sectors
sectors 35..67  root directory (512 entries of 32 bytes)
sector 67 on    data area, divided into clusters (here, 1 sector each)
```

- The **boot sector** says the size of the sector and of the cluster, where each
  region starts, and how many sectors the volume has. The reader validates each field before
  trusting any of them (signature, sectors per cluster a power of 2, total
  sectors that fits on the device, the cluster count between 4085 and
  65524, which is what makes it a real FAT16 volume...). Each refusal has its own
  reason, which appears in the message (`volume FAT invalido: assinatura`).
- The **FAT** is an array of 16-bit numbers, one per cluster. The entry for
  cluster `c` says which cluster comes **after** `c` in the same file; a special value
  (`0xFFF8` to `0xFFFF`) marks the end of the chain. A file is a linked
  list of clusters, and the FAT is the list.
- The **root directory** is a fixed region of 32-byte entries: name in
  8.3 format (8 characters, 3 of extension, uppercase, padded with
  spaces), attributes, first cluster, and size. A subdirectory is an ordinary
  file whose content is entries, and it lives in the data area.
- Clusters are numbered from **2** (numbers 0 and 1 of the FAT are
  reserved), so cluster `c` starts at sector `data_start + (c - 2)`.

Why FAT16, with 1 sector per cluster and about 2 MiB: FAT12 packs 12 bits
(an entry crosses two bytes), FAT32 requires volumes of tens of MiB, and FAT16
with fewer than 4085 clusters would be read as FAT12 by any tool. A
cluster the size of a sector makes the concept visible: a 536-byte file
already occupies two clusters and needs to follow the chain.

### How `read` walks a chain, and why it does not trust it

Reading a file is: starting from the first cluster, copy the bytes of each cluster
and follow the FAT until the file's size runs out. The reader stores in the cursor (the
read position) which cluster the position falls in, so the next read
continues from there instead of restarting the chain. But the chain comes from the disk, and the disk
can be wrong. Three defenses, all of the same kind (never trust a number
that came from outside):

1. **Every cluster number is validated before becoming a sector.** Only clusters
   `2` to `cluster_count + 1` exist. A FAT entry that points outside that range, to
   a free cluster (`0`), reserved, or marked as a bad sector,
   in the middle of a chain, is `Corrupt`.
2. **Every traversal has a step limit.** A chain with a cycle
   (`c → d → c`) never ends by itself; but a file whose size requires more
   clusters than the volume has is refused, and a directory walks at most
   512 entries. A cycle becomes an error in a small number of steps, never an
   infinite loop.
3. **The size is checked against the chain.** A file that declares 5000 bytes
   and has a two-cluster chain delivers the 1024 bytes that exist and, on the next
   call, the error. A size greater than zero with no cluster
   at all is also an error.

All arithmetic with values from the disk uses `checked_*`, and no slice index
depends on an unchecked value. The result is `FatError`, never a
panic. The reader's tests fabricate each of these bad images with the `fatimg` crate
and change a few bytes on purpose.

Names: `.` and `..` of subdirectory entries, deleted entries (`0xE5`),
volume labels, and **long-name** entries (attribute `0x0F`, a FAT trick for
storing names longer than 8.3 across several entries) are ignored. Long
names are out of scope.

### ATA via PIO

The IDE disk has a few registers on I/O ports. On the primary channel, from
`0x1F0` to `0x1F7`: data, sector count, the LBA in three bytes, the register
that chooses the disk (master or slave), and the command/status one. Plus one
control register at `0x3F6`. Reading a sector is a short conversation:

1. choose the disk and the 4 high bits of the LBA, and wait 400 ns (four reads
   of the alternate status);
2. wait for the disk to release the `BSY` (busy) bit;
3. write the count (1) and the LBA, and send the `READ SECTORS` command (`0x20`);
4. wait for `BSY` to clear and `DRQ` (data ready) to set;
5. read 256 16-bit words from the data port.

"PIO" means the **processor** copies the bytes, one word at a time; with
DMA the controller would copy on its own into memory (and the kernel would have to have
contiguous physical memory for that). To find out whether there is an ATA disk and how large
it is, the driver sends `IDENTIFY` (`0xEC`): status `0x00` or `0xFF` after
choosing the disk means absence; a different signature in the LBA registers means
another type of device (ATAPI, SATA); and words 60 and 61 of the response are the
total number of sectors.

Two decisions keep the driver small and safe:

- **No interrupt.** The `nIEN` bit of the control register turns off the disk's IRQ,
  and the PIC does not change: it still has only the timer (IRQ0) and the keyboard (IRQ1).
  Instead of sleeping until the disk signals, the kernel does **polling**: it reads the status
  register in a loop until the disk responds. There is no mechanism for blocking a
  task waiting for the disk, and for this milestone the kernel simply waits.
- **Every wait has a limit.** A polling loop with no limit would hang the kernel
  forever if the disk did not respond. The `wait` function reads the status at most
  100,000 times and then gives up with `Timeout`. It does not use a clock: the limit is a
  count of reads, which makes it possible to test without a disk (a closure that always
  returns "busy" times out after exactly `max` reads).

### Why disk reading is atomic with respect to the scheduler

Reading a sector is a sequence of port accesses that cannot be interleaved
with another: if other code touched the controller in the middle, the registers
would become inconsistent. The Milestone 7 rule already guarantees this: the kernel is **never
switched**, the timer only switches programs when it interrupts ring 3, and an
interrupt that arrives in ring 0 only sends the EOI and returns (syscalls run with
`IF` off). Since the disk is read inside the kernel, no task switch
can land in the middle of the conversation with the disk. The driver makes the rule explicit in
the code: the whole sequence runs inside `without_interrupts` and under a
controller lock, so that it keeps holding even if the scheduler's policy
changes one day.

### How the images are generated and reach QEMU

Nobody assembles a volume by hand. `build.rs`, inside the same `cargo run` or
`cargo test`, uses the internal `fatimg` crate (a FAT16 volume builder in
~200 lines, `no_std` and dependency-free) to generate:

- `ramdisk.img` from `discos/ram/`, which the kernel embeds with
  `include_bytes!`;
- `target/imagens/disco.img` from `discos/disco/`, plus the ELF of
  `visita` (the program that exists only on the disk) and a 65,537-byte file that
  exists only to prove the refusal of an executable that is too large;
- `target/imagens/corrompido.img`, the disk with the boot sector zeroed, for the
  tests.

All are assembled in memory before any file is written, and an error
ends the script: an absent, partial, or out-of-date image never comes out. The
same crate fabricates and tampers with images inside the kernel tests. The disk
reaches QEMU through the `bootimage` arguments in `Cargo.toml`: the boot disk
is the primary master, `disco.img` is the primary slave (`index=1`), and in the tests
`corrompido.img` is the secondary master (`index=2`), while the secondary slave
is left empty on purpose, to prove that the absence of a disk does not hang things. The option
`snapshot=on` sends writes to a temporary QEMU file, so the
image never changes (`readonly=on` is refused by QEMU on IDE disks).

### Volumes, paths, and each program's file table

`src/fs.rs` knows the two volumes by prefix (`/ram`, `/disco`) and the state
of each: mounted, or **unavailable** with a reason (no disk, device
that is not ATA, invalid boot sector, read error). Boot never panics
because of a volume: it writes one line per volume to the serial port and moves on.
A path is validated without using the heap (volume, up to 8 components, 8.3 names, at
most 64 bytes) and `.` and `..` are **refused**, so no path can
leave the volume.

Each program has **its own** `FileTable`: four fixed slots inside the
`Task`, without heap. The descriptor the program sees (`0` to `3`) is the slot
index, always the lowest free one, and each slot stores where the file lives and the
read position. Since the table is a field of the task, a program never
sees another's descriptors or read positions: two programs that
open the same file each read from their own point. When the task ends (through
`exit` or an error), the `Task` is destroyed and the table's `Drop` closes whatever
was left; a global counter is what the tests read to prove that nothing was left
open.

The four syscalls (`SYS_OPEN`, `SYS_READ`, `SYS_CLOSE`, `SYS_READ_DIR`) follow
the usual rule: the kernel trusts nothing that comes from the program. The path is
copied into an array on the kernel stack after being validated; the read buffer
is checked (in the user region, mapped, **writable**) before touching the
disk; an error returns a contract code (`ERR_NOENT`, `ERR_BADF`...) and the
program **keeps running**. A directory is opened like a file and read one
entry at a time (`SYS_READ_DIR`), with the cursor stored in the descriptor.

### How `run` loads an executable from a file

`run /disco/bin/visita` resolves the target before starting anything: it reads the
**whole** file into the kernel heap (refusing, before reading, a file
larger than 64 KiB) and hands the bytes to the same `run_images` as the
embedded programs. From there on it is the Milestone 5 path: `elf::parse` validates the ELF
**before** any page is mapped, so a text file in place of
a program is refused without touching memory. The kernel heap went up to 16
MiB: up to 4 executables of 64 KiB read at the same time, and the reader's tests
fabricate 2 MiB volumes in memory.

A detail: the name of an embedded program is text that lives forever, but
the name of a program read from a path is born from something typed. Storing it as
`&'static str` would require leaking memory on every `run`; that is why the task's name is
a `ProgramName`, a copy of up to 16 bytes that lives inside the `Task` itself.

### What was left out

Writing, creating, and removing files, FAT long names, attributes,
permissions and dates, partitions, more than one disk, block cache, DMA and
disk interrupts, and streaming reads of an executable remain out of
scope. The ATA driver exists to serve the file system; writing is left
for Milestones 10 (ramdisk) and 11 (ATA disk).

## Milestone 9: the real-time clock

os-rust already had four drivers without having used the word: VGA text, the serial
port, the PS/2 keyboard, and the ATA disk. Milestone 9 adds the fifth, and picks the
smallest possible: the **real-time clock** (RTC), the chip that keeps the date and
time with its own battery, even with the computer off. It is small,
but it closes the complete cycle the project always shows: hardware, driver in the
kernel, syscall, runtime library, user program. And it hides four
pitfalls worth a lesson.

### Two ports and an index

The chip is not in the memory space: it sits behind two **I/O ports**.
You write to `0x70` the number of the register you want and read the value from
`0x71`. The registers that matter: `0x00` seconds, `0x02` minutes, `0x04`
hours, `0x07` day, `0x08` month, `0x09` year, and `0x32` century, plus two status registers,
`0x0A` and `0x0B`. All the conversation with the hardware is in two small functions of
`src/rtc.rs` (`cmos_read` and `read_regs_once`); the rest of the driver is arithmetic
on values already read, and so can be tested with no chip at all.

When choosing the register, the driver keeps bit 7 of the index clear
(`reg & 0x7F`): that bit is the NMI interrupt mask on the same port, and this
milestone has no reason to touch it.

### First pitfall: BCD or binary

In **BCD** (binary-coded decimal), each nibble holds a decimal digit:
the number 26 comes as `0x26`, not as `0x1A`. Reading `0x26` as if it were binary
would give 38. Bit 2 of register `0x0B` says which format the chip uses, and the driver
handles both. A nibble greater than 9 (`0x1A`) is not valid BCD, and the driver
refuses it instead of inventing a number.

### Second pitfall: 12 or 24 hours

Bit 1 of `0x0B` chooses 24-hour mode. In 12-hour mode, bit 7 of the
hour register marks **PM** and the hour goes from 1 to 12. The rules that trip people up:
12 AM is midnight (hour 0), 12 PM is noon (hour 12), and 1 PM to 11 PM
add 12. The driver separates the PM bit from the number before converting, and rejects
an hour outside 1 to 12 in that mode.

With BCD and binary, 12 and 24 hours, there are four possible combinations of the same
chip, and the driver's first test checks that all four give exactly the same
instant.

### Third pitfall: the update window

Once per second the chip rewrites the registers, and that takes some time. If the
driver reads in the middle, it may get a mixed date: 23:59:59 already with the day
incremented, for example. Bit 7 of register `0x0A` (UIP, *update in
progress*) signals that the update is in progress.

The driver does two things. First it **waits for UIP to drop**, with a limit of
100,000 polls (a chip that never responds cannot hang the kernel; the error is
`indisponivel`). Second, it **reads twice and compares**: if the two reads are
equal, it is confirmed; if they differ, the chip rolled over the second in the middle, and it tries
again, up to 5 times. If it never stabilizes, the error is `instavel`. Waiting for UIP
would not be enough on its own, because the update can start right after the check; the
second read is the proof. The `read_consistent` function receives whatever reads the chip as a
parameter, and that is why the tests simulate a chip that rolls over the second in the middle.

### Fourth pitfall: the year has two digits

Register `0x09` holds only the last two digits of the year: 2026 comes as 26.
Some chips have a **century** register (`0x32`, which is 20 in 2026);
others do not, and it comes zeroed. If the century exists and is valid, the year is
`century * 100 + year`. If not, the driver uses a fallback rule: from 70 to 99 it is
19xx, from 00 to 69 it is 20xx. This way 2026 appears as `2026` and never as `0026`.

### What the driver validates, and what it does not compute

After converting, the driver checks the ranges (month from 1 to 12, hour from 0 to 23,
minute and second from 0 to 59) and the day against the month, taking leap years into account:
February 31 and February 29, 2025 do not exist, and the driver returns
`relogio invalido` instead of an impossible value. A year is a leap year if it is
divisible by 4, except centuries not divisible by 400 (2000 was, 1900
was not). This is only **rejecting**: the driver does not compute the rollover of a day, month, or
year, which comes from the chip. And the kernel never panics because of a bad clock:
the `data` command shows the message, and the syscall returns `ERR_CLOCK`.

### Why polling, and not the chip's interrupt

The RTC can generate an interrupt (IRQ8) every second or at an alarm. This milestone
does not use it: reading the time on demand is simpler, the PIC still has only the timer and
the keyboard, and nothing needs to happen *when* the second rolls over. Whoever
wants to wake a program at 7 a.m. will need the interrupt; whoever only asks
"what time is it?" does not.

### Why the read is atomic

The pair "choose the register, read the value" cannot be interleaved with another
pair: if an interrupt switched programs between the two `out`/`in` and the other
program also read the clock, the value read would be that of the wrong register.
`rtc::read` runs entirely with interrupts off
(`without_interrupts`), and the syscall already runs that way. Result: two programs
asking for the time at the same time (`run hora hora`) never receive a mixed value.

### From the chip to the program: `data`, `SYS_TIME`, and `hora`

The complete path, from the bottom up:

1. `rtc::read()` returns a `DateTime` (`abi`) or an `RtcError`.
2. The `data` command (`src/shell.rs`) writes it with `{}` and appends ` UTC`.
3. The `SYS_TIME` syscall (10, contract version 5) validates the size (exactly 8
   bytes) and the pointer (through the same path as the other syscalls) and only then reads the
   clock and writes the `DateTime` into the program's buffer. A bad buffer is
   refused without even touching the chip.
4. The runtime library hides the syscall behind `time::now()`.
5. The `hora` program calls `time::now()` and writes the result.

`DateTime` lives in the `abi` crate because the kernel and runtime need to agree on the
layout of the 8 bytes (year in 2 bytes, then month, day, hour, minute, second, and one
alignment byte), and the `Display` lives alongside it, so `data` and `hora` show
exactly the same text.

### UTC only

QEMU hands the chip the host computer's time in UTC, and the kernel
shows it as it came, with the `UTC` suffix. Time zones and daylight saving time
are policy, not hardware, and are left out: a program that wants local time
adds the difference.

### How the milestone is tested without depending on the real time

The conversion is tested with fabricated registers (`src/rtc.rs`), without touching any
port: the four format combinations, midnight and noon, impossible values, the century,
the leap year, and read repetition. The tests inside QEMU (`tests/relogio.rs`) only
check what is true on any day: the year is in a plausible range, and two consecutive reads
do not go backward.

### What was left out

Setting the clock (writing to the RTC), the IRQ8 interrupt and the alarm, time zones
and daylight saving time, and any calendar computation beyond rejecting
dates that do not exist. Writing, incidentally, comes back elsewhere: 
Milestones 10 and 11 teach the kernel to write to files.
